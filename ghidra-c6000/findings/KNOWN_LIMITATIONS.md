# 已知限制

## 1. 反编译器的 "Overlapping input varnodes"

现象:`c0098b98`(槽激活)、`c00989e4`(预算检查)在完整固件上下文中
反编译失败,报 `Low-level Error: Overlapping input varnodes`;
`c0098784`(槽激活链)在干净导入下同样触发,仅有历史函数状态时
得到过一次 9.7KB 的部分输出(见 `examples/decompiled/fn_c0098784.c`)。

根因:寄存器对(如 `MPYLI A0,A11,A1:A0`)的"局部 64 位拼/拆"建模,
在被调用方/寄存器传递分析中与函数输入集合发生部分重叠。单独取函数体
字节做最小复现时**可以正常反编译**,因此是指令上下文组合触发,
不是单条指令的问题。

排查记录:

- 函数体二分:0x18/0x80/0x280 等长度在真实程序中均失败,最小 ELF
  (同字节、带/不带返回、带/不带尾部包头)全部成功 → 与程序整体状态
  相关,而非函数体内容本身。
- 向 `insn_map` 加入取指包头伪指令后,函数体可以穿过包头,但更多
  函数进入同一失败路径(不能作为修复方案)。
- 原始 pcode 扫描未发现输入重叠(排除常量与相同输入后)→ 重叠由
  反编译器输入恢复阶段产生,而非 Sleigh 构造器直接产出。

可能的修复方向:
- 把 `_pair_local` / `_split_pair` 改为 `PIECE`/`SUBPIECE` 语义,
  或定义显式 64 位重叠寄存器(需处理别名);
- 对这些函数用"拆成 32 位寄存器读写"的保守建模;
- 或接受 Ghidra 12.1.2 的该限制,改用更高版本/不同反编译器验证。

## 1b. 代码区嵌入数据表(当前主要阻塞)

把寄存器对改为真实 64 位寄存器后,"Overlapping input varnodes"已消失,
但 `c0098b98` / `c00989e4` / `c0098784` 仍无法干净反编译,新的失败模式:

```
WARN Decompiling c0098b98, pcode error at c00cebec:
     Unable to resolve constructor at c00cebec
WARN Decompiling c0098b98: Unable to read bytes at ram:0000df30 ...
```

根因(已定位):

- 固件代码区里嵌有**数据表**(如 `c00ceb00` 一带,字节
  `0x60606060`/`0x0c0c0c9c` 等明显是表数据,dis6x 也把其中部分
  标记为 `.word` 无法解码)。
- dis6x 把这些表字节部分解码成"伪指令",反编译器沿调用/分支流
  走进该区域,遇到 `.word` 空洞(`c00cebec`)就报 pcode error;
  另外部分表数据被解释成地址(`0xdf30` 等),反编译器去读未映射
  内存产生 "Unable to read bytes"。
- 已确认无任何 Sleigh 构造器直接引用这些地址,错误完全来自
  反编译器分析阶段的流探索。

已尝试并确认无效/不充分的手段:

- 向 insn_map 加入取指包头伪指令(让函数体穿过包头)→ 更多函数
  进入失败路径。
- 为全部 CALLP 目标预建函数(1325-1602 个)→ 消除调用越界,
  但分支流仍会走进数据区。
- 函数体在 CALL/RETURN/无条件分支处截断 → 减少了吞并,但
  流探索仍能沿条件分支进入数据区。

剩余修复方向:

- 为**全部 B/BNOP 分支目标**也预建函数边界;
- 或在生成阶段把"数据表区域"整体标注为非代码(需要更强的
  dis6x 语料分类:哪些区域是表、哪些是真代码);
- 或接受 Ghidra 12.1.2 的限制,把这三个函数的手工分析结论
  (见 `B1ON_G1ON_RE.md`)作为最终交付。

## 2. 少数数据空洞(39 处)

固件中存在分支目标指向**不可解码数据字**(dis6x 也无法解码)的情况,
已用 NOP 构造器填平,反编译器会在这些点截断控制流并给出
`WARNING: Bad instruction`。属于真实固件特性,不影响其它函数的分析。

## 3. 16 位指令的"合成字"模式

重建镜像中的 16 位指令使用合成编码,因此本模块**不能直接解码原版
compact 字节流**(那需要取指包上下文,超出 Ghidra 线性模型)。
对任意新固件,需先跑一遍 `dis6x` 语料生成。

## 4. 指令语义近似

饱和运算(SADD/SMPY 等)、SIMD 车道运算(ADD2/PACK* 等)在语义表中
以普通标量/位运算近似;反编译结果在溢出/边界行为上可能与硬件不同。
解码层面完全一致,语义层面以文档标注为准。
